# 可观测性指南 — 让运行中的系统可调试

门禁证明的是交付*之前*的行为：验证命令退出 0。可观测性是另
一半——系统在*运行中*出问题时，能不能只靠它输出的东西查清原
因，而不必挂调试器、或在观察下重跑一遍。本指南是使用
agent-harness 的项目的轻量约定，故意做小：三个习惯，一个调试
闭环。

## 1. 带 trace id 的结构化日志

每行一个 JSON 对象，输出到 stdout（CLI 写文件也可以）。最少
字段：

| 字段 | 含义 |
|---|---|
| `ts` | UTC 时间戳，ISO 8601 |
| `level` | `debug` / `info` / `warn` / `error` |
| `trace_id` | 每个工作单元一个 id（请求、任务、CLI 运行、会话） |
| `component` | 输出这一行的模块/子系统 |
| `event` | 稳定的机器可读事件名（`reminder_sent`） |
| `msg` | 人读的细节；变量放独立字段，不要拼进字符串 |

让日志值得留的规则：

- **在入口处生成 `trace_id`**（HTTP 请求、队列任务、CLI 调用），
  并透传到每一次调用、队列消息和子进程。无法跨组件关联的
  故障，是三个谜团，不是一个。
- **记决策，不只记错误**：收到的输入（id、计数——不是载荷）、
  走的分支、发出的外部调用（目标、耗时、状态）、重试、每个
  工作单元的最终结果。只有一行 error、前面没有 info 的日志
  是死路。
- **绝不记录密钥与个人数据**：不记 token、密码、凭据、用户
  内容原文。记事物的 *id*，不记事物本身。脱敏属于日志调用
  本身，不属于事后的清洗环节。
- 事件名保持稳定。改一个 `event` 名会废掉所有存量查询和基于
  它的调试习惯——按 API 对待它。

## 2. 一条健康检查命令

每个项目有且只有一条健康检查命令，契约如下：

- **名字/位置**：一个显眼的位置——`scripts/healthcheck`、项目
  清单里的 `health` 脚本，或项目在 `PROJECT_CONTEXT.md` 里写明
  的等价物。
- **行为**：检查系统干活真正依赖的东西（数据存储可达且迁移
  已应用、队列/缓存可达、必需配置存在），每个检查输出一行
  （`ok`/`FAIL` + 名称 + 简短说明），全部通过才退出 0。
- **便宜且只读**：以秒计，不是以分钟计；不写数据、不修复、
  不用重试掩盖抖动的依赖。会修东西的健康检查是穿了马甲的
  部署脚本。
- 任何故障报告后第一个跑它，任何修复之后最后一个跑它。

## 3. 接入门禁

健康检查的价值在于 harness 不用人催就跑它：

- 放进 `gate/clean-state.json`。五个维度的槽位是固定的，所以
  要组合：链进 `start`（走标准启动路径，然后探活——例如
  `"start": "<启动命令> && <健康检查命令>"`），或在它足够快
  时链进 `test`。这样 `check-clean` 会拦住"能启动但不健康"
  的交接。
- 把它用作（或作为一部分用作）运行时健康类功能清单项的
  `verification.command`：这样的 `passing` 意思是"运行中的
  系统回答了健康"，而不只是"代码存在"。
- 把命令本身记进 `PROJECT_CONTEXT.md`，挨着构建/测试/启动
  命令，让下一个会话不用考古就能找到。

## 4. 基于日志的调试闭环

运行中的系统出问题时：

1. **先从日志复现。** 找到出问题的工作单元和它的 `trace_id`，
   动代码之前把整条链读完。记下最后一个*符合预期*的事件和
   第一个*不符合预期*的事件——bug 就在两者之间。
2. **一句话写出假设**："组件 X 收到了 Y 却输出了 Z，因为……"。
   如果链路既不能证实也不能证伪它，这个缺口就是可观测性
   债务——明说出来。
3. **有缺口先补可观测性，再修 bug。** 补上缺失的日志行
   （稳定的事件名、记 id 不记载荷），重跑，然后才修行为。
   否则下一次事故还是从同样的盲区开始。
4. **修完后回归检查两次**：自动化测试套件，以及当初暴露
   故障的*同一条日志查询*——它现在必须显示健康的链路。
   没人重新观察过的修复是希望，不是验证。
5. **闭环**：事故若暴露出一类故障，补上能更早抓住它最便宜
   的护栏（一个测试、一个健康检查、对该事件名的告警）；
   若改变了约定，记进项目的决策日志。

## 5. 清单

- [ ] 日志为每行一个 JSON，含 `ts`、`level`、`trace_id`、
      `component`、`event`
- [ ] `trace_id` 在入口生成并全程透传
- [ ] 任何日志字段都不含密钥或个人数据
- [ ] 一条有文档的健康检查命令；退出 0 = 健康；只读；秒级
- [ ] 健康命令已接进 `gate/clean-state.json` 并写明在
      `PROJECT_CONTEXT.md`
- [ ] 上一次事故是靠链路查清的，其可观测性缺口（如有）补的
      是日志行，而不只是修复
