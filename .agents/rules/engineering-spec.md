# Engineering Specification & Quality Gates (工程方法论与质量门禁)

> 本规则定义规范驱动开发（SDD）、测试驱动开发（TDD）及代码极简原则。

## 1. 规范先行（Spec-Driven Development）
- **需求不可含糊**：对于目标或验收标准不清晰、影响多个模块的改动，开始实现前应明确：
  - 核心目标（In-Scope）与非目标（Out-of-Scope）；
  - 验收场景（清晰的输入与预期输出）。
- **变更先改规范**：若实现过程中发现原有设计或接口契约需要调整，先向用户说明变更点，禁止静默偷换实现。

## 2. 验证证据门（TDD & Verification Gate）
- **真实验证闭环**：任务完成判定不依赖 Agent 的主观声称，必须出示以下至少一种物理证据：
  - 自动化测试运行通过的真实终端输出（测试用例名称、通过数）；
  - 针对 Bug 编写的最小复现测试（先证明红，修复后变绿）；
  - 手动验证的执行命令、预期与实际响应。
- **不可验证时明确说明**：若因环境限制（如缺少硬件、外部网络阻断、缺少私有数据库）无法运行验证，必须显式列出未验证项及建议的人工验证步骤。

## 3. 代码熵减与懒人阶梯（Ponytail 极简准则）
写代码前必须走一遍极简决策阶梯：
1. **必要性检查**：这个功能/字段是否真正被需要？（严禁过度超前设计，拒绝 YAGNI）；
2. **复用检查**：当前项目中是否已有相似工具函数或组件可复用？
3. **标准库优先**：该需求能否用语言标准库原生完成？坚决不为单功能引入沉重的第三方外部依赖；
4. **最小且清晰**：改动局限在满足全部明确需求的最小作用域；不以行数最少为目标，不牺牲可读性、兼容性、安全性或数据完整性。
5. **先理解再简化**：编码前了解受影响的实现与调用路径。CodeGraph 可用时优先语义探索，否则使用限定范围的定向搜索；修复问题时解决根因，不在单一调用点掩盖共享缺陷。
6. **范围与确认**：不得擅自缩减用户明确要求的交付范围。必要信息或授权缺失时，先澄清再执行依赖该答案的操作；对非必要扩展可说明取舍，不阻塞已明确的工作。

## 4. 活体文档与追溯门禁（Living Documentation & Traceability Gate）
- **文档即工程制品**：项目长期技术文档集中维护在 `docs/`（需求 `specs/`、架构 `architecture/`、接口与配置参考 `reference/`、用户操作指南 `guides/`），头部通过 YAML Frontmatter 声明 `modules`（关联代码路径）与 `depends_on`。
- **分级变更履约**：
  - **L0 微调**（内部 Bugfix、不改对外接口/配置）：不要求修改系统文档，仅维护会话断点或错题本；
  - **L1 接口/配置改动**（改动 1~2 个 API、调整配置文件项）：必须同步更新 `docs/reference/` 下的对应参考；
  - **L2 重大功能/架构调整**（新增模块、重构协议）：必须履约四阶文档闭环（需求 $\to$ 架构 $\to$ 接口/配置 $\to$ 操作指南）。
## 5. 决策所有权与澄清三界线（Decision Ownership & Clarification Boundaries）
在交互与需求明确阶段，严格区分三类事实，禁止向用户推卸技术责任或无证据盲猜：
- **可调查事实（Investigable Facts）**：可以通过代码检索、环境检查、本地配置直接获取的事实（例如“项目中是否有某个函数”、“依赖版本”、“编译指令”），**严禁向用户提问**，Agent 必须先自主调查并以事实说话。
- **用户决定（User Choices）**：对于业务目标、功能范围（In/Out-of-Scope）、产品可见行为、不可逆架构选型或存在互斥方案的技术抉择，Agent 应动态分析各选项影响并给出推荐，提请用户明确确认。
- **实现选择（Implementation Choices）**：严禁把实现层面的专业技术决策（如内部算法实现、数据结构选型、常规函数拆分、内部变量命名等）作为问题甩给用户，模型必须专业自主决策并对代码质量全权负责。

## 6. 独立核验员准则（Independent Verifier Protocol）
- **候选实现原则（Candidate Implementation）**：实现者（Builder）提交的代码、配置与文档仅被视为“候选产物”，绝不可仅凭实现者主观陈述断言任务完成。
- **独立验收闭环**：在关键任务验收或复杂交付时，必须以隔离的只读核验视角（或调度只读 Verifier 子代理），对照需求 Spec、验收场景与测试执行物理证据逐项比对：
  - 只有全部验收场景均具备物理证据支撑时方可判定通过；
  - 存在未通过项、断言失败或缺失证据时，必须带回具体失败根因，重新进入实现阶段修复。
