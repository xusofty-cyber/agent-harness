# Engineering Specification & Quality Gates (工程方法论与质量门禁)

> 本规则定义规范驱动开发（SDD）、测试驱动开发（TDD）及代码极简原则。

## 1. 规范先行（Spec-Driven Development）
- **需求不可含糊**：对于目标或验收标准不清晰、影响多个模块的改动，开始实现前应明确：
  - 核心目标（In-Scope）与非目标（Out-of-Scope）；
  - 验收场景（清晰的输入与预期输出）。
- **变更先改规范**：若实现过程中发现原有设计或接口契约需要调整，先向用户说明变更点，禁止静默偷换实现。

## 2. 验证证据门（TDD & Verification Gate）
- **真实验证闭环**：任务完成判定不依赖 Agent 的主观声称，必须出示以下至少一种物理证据：
  - 自动化测试运行通过的真实终端输出（测试用例名称、通过数）；
  - 针对 Bug 编写的最小复现测试（先证明红，修复后变绿）；
  - 手动验证的执行命令、预期与实际响应。
- **不可验证时明确说明**：若因环境限制（如缺少硬件、外部网络阻断、缺少私有数据库）无法运行验证，必须显式列出未验证项及建议的人工验证步骤。

## 3. 代码熵减与懒人阶梯（Ponytail 极简准则）
写代码前必须走一遍极简决策阶梯：
1. **必要性检查**：这个功能/字段是否真正被需要？（严禁过度超前设计，拒绝 YAGNI）；
2. **复用检查**：当前项目中是否已有相似工具函数或组件可复用？
3. **标准库优先**：该需求能否用语言标准库原生完成？坚决不为单功能引入沉重的第三方外部依赖；
4. **最小且清晰**：改动局限在满足全部明确需求的最小作用域；不以行数最少为目标，不牺牲可读性、兼容性、安全性或数据完整性。
5. **先理解再简化**：编码前了解受影响的实现与调用路径。CodeGraph 可用时优先语义探索，否则使用限定范围的定向搜索；修复问题时解决根因，不在单一调用点掩盖共享缺陷。
6. **范围与确认**：不得擅自缩减用户明确要求的交付范围。必要信息或授权缺失时，先澄清再执行依赖该答案的操作；对非必要扩展可说明取舍，不阻塞已明确的工作。
