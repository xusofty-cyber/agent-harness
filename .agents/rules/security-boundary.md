# Security Boundaries & Protection (安全边界与高危防呆)

> **适用场景**：涉及敏感数据处理、危险命令执行、生产发布、权限边界、以及触碰核心架构与配置的高风险操作。
> **核心原则**：**所有高风险操作必须停下向人类确认意图并说明影响面；凭证与敏感数据零泄露；严禁不可逆盲目修改。**

---

## 1. 八大高风险操作确认矩阵（High-Risk Matrix）

遇以下操作，模型在执行前**必须停下向人类明确确认**，说明变动内容、潜在风险与影响面：

| # | 操作场景 | 典型文件/命令特征 | 潜在风险与破坏性 | 标准处理规约 |
|---|---|---|---|---|
| **1** | **构建配置变更** | 修改 `.pro` / `CMakeLists.txt` / `package.json` / `Cargo.toml` / `pom.xml` | 影响全项目构建链、依赖解析、编译宏与链接库 | 改前列出变动项确认 + 全量构建回归验证 |
| **2** | **引入新依赖** | 新增第三方库、包管理器 install 新包 | 依赖膨胀、开源许可/商用合规风险、环境构建链污染 | 改前确认必要性，优先考虑标准库（Ponytail 阶梯） |
| **3** | **改核心公共数据结构** | 修改全局公共头（如 `public_struct.h`、`types.ts`、`models.py`） | **影响面最广**，引发数十个源文件级联编译报错 | 改前确认 + 运行图谱（`codegraph explore`）评估调用链 |
| **4** | **改核心管理器/公共接口** | 修改核心调度单例、全局核心 Service、Controller 公共接口 | 核心调度逻辑被击穿，单例调用点极多（隐式依赖深） | 改前确认，禁止随意变更入参/返回值，保证向下兼容 |
| **5** | **改通信协议/报文契约** | 修改协议定义（如 `protofile/` 下 JSON、Protobuf、通信报文定义） | 设备通信中断、解析/组包/UI/发布全链路脱节 | 改前确认，必须严格对照协议说明书，两端对齐 |
| **6** | **改安全与授权代码** | 修改软件授权许可（`license`）、加解密密钥、身份认证拦截器 | 软件保护机制被破坏或安全加固失效 | 改前确认，严禁降低安全强度或绕过授权校验 |
| **7** | **改忽略规则与 CI/CD** | 修改 `.gitignore`、`.github/workflows/`、Docker 构建脚本 | 误忽略关键文件、误将垃圾/敏感文件推上远端、破坏构建流水线 | 改前确认，说明每一行规则调整的原因 |
| **8** | **跨模块/大规模改动** | 一次性改动涉及 3 个以上文件，或跨越前后端/底层公共库边界 | 回归面过大，极易引发难以排查的隐式副作用 | 改前确认，拆分为打勾任务清单，小步迭代验证 |

## 2. 生产环境与高危命令强制阻断

以下操作一旦检测到，必须**无条件拒绝执行**或**进行最高级别警示**：
1. **线上生产环境写入**：针对生产环境数据库执行 `DROP DATABASE`、`TRUNCATE TABLE`、或未带 `WHERE` 的 `UPDATE`/`DELETE`；
2. **破坏性文件删除**：未核实路径的 `rm -rf`、`Remove-Item -Recurse`，严禁在根目录或项目源码根目录执行通配删除；
3. **重写 Git 历史**：严禁 `git push --force`、受保护分支 `rebase`；
4. **网络安全组与计费资源**：严禁未经授权修改安全组放行 `0.0.0.0/0`、关闭防火墙或创建高额计费资源。

---

## 3. 凭证与敏感数据零泄露

1. **绝对禁止硬编码**：
   - 严禁在代码、注释、提交历史、文档、输出日志中明文记录 API Key、Token、密码、证书私钥（`.pem`, `.key`, `id_rsa`）、生产环境连接串。
2. **误操作防御拦截**：
   - 包含密钥配置的文件（`.env.local`, `credentials.json` 等）必须在加入 `.gitignore` 之后方可使用；
   - 任何输出到终端或控制台的信息，涉及手机号、身份证、密钥等字段必须掩码脱敏。

---

## 4. 超大文件（>100KB）安全维护准则

针对老旧遗留代码或超大型源文件（如 >150KB 的核心管理器/协议解析器）：
- **定位精细度**：严禁盲目重构整块文件；改动前先通过精准行号或符号定义定位局部，仅做外科手术式微调；
- **风格一致性**：新增代码必须严格贴合当前文件原有的命名规范与缩进习惯，严禁在同一文件内混杂异构风格；
- **增量验证**：超大文件修改后，必须运行针对性单测或构建检查，确保无连锁破坏。
