# Security Boundaries & Protection (安全边界与高危防呆)

> **适用场景**：涉及敏感数据处理、危险命令执行、生产发布、权限边界、以及触碰核心架构与配置的高风险操作。
> **核心原则**：**所有高风险操作必须停下向人类确认意图并说明影响面；凭证与敏感数据零泄露；严禁不可逆盲目修改。**

---

## 1. 八大高风险操作确认矩阵（High-Risk Matrix）

按操作的影响和可逆性采取分级措施。下表中的默认动作分别是“审慎处理”或“必须授权”；若用户已经明确要求该具体操作，不重复索取相同授权，但仍需遵守绝对禁止项和安全边界。

| # | 操作场景 | 典型文件/命令特征 | 潜在风险与破坏性 | 标准处理规约 |
|---|---|---|---|---|
| **1** | **构建配置变更** | 修改构建、打包或依赖配置 | 可能影响构建链与发布产物 | 评估影响并验证相关构建；只有涉及高风险环境或破坏性变更时必须授权 |
| **2** | **引入新依赖** | 增加第三方依赖或执行会改变依赖清单的安装命令 | 许可、供应链和维护成本 | 说明用途、替代方案和许可影响；依项目授权政策决定是否等待确认 |
| **3** | **公共数据结构或 API** | 修改对外类型、公共头、接口契约 | 下游兼容性和调用方影响 | 检查调用方、兼容策略并运行针对性验证；破坏兼容时先确认迁移方案 |
| **4** | **核心管理器/公共接口** | 修改核心调度、认证或共享服务接口 | 可能影响多个调用链 | 先追踪影响面并定义验收；高风险或需求不明确时暂停澄清 |
| **5** | **通信协议/报文契约** | 修改协议定义、序列化格式或跨服务契约 | 可能造成版本不兼容或数据损坏 | 明确两端兼容和迁移策略；无兼容方案时必须先确认 |
| **6** | **安全与授权代码** | 修改认证、授权、密钥处理或安全控制 | 可能削弱安全边界 | 不得降低安全控制或暴露凭证；变更安全边界前必须确认 |
| **7** | **忽略规则与 CI/CD** | 修改 `.gitignore`、流水线或发布脚本 | 可能影响交付和仓库内容 | 说明影响并检查敏感文件/流水线结果；高影响发布变更先确认 |
| **8** | **跨模块/大规模改动** | 影响多个模块或外部契约 | 验证范围增大 | 拆分计划并做相称验证；文件数量本身不要求授权 |

## 2. 生产环境与高危命令强制阻断

以下操作一旦检测到，必须**无条件拒绝**或按要求等待明确授权：
1. **线上生产环境写入**：针对生产环境数据库执行 `DROP DATABASE`、`TRUNCATE TABLE`、或未带 `WHERE` 的 `UPDATE`/`DELETE`；
2. **破坏性文件删除**：未经确认的不可逆批量删除；核实目标和影响后再执行；
3. **重写 Git 历史**：严禁 `git push --force`、受保护分支 `rebase`；
4. **网络安全组与计费资源**：严禁未经授权修改安全组放行 `0.0.0.0/0`、关闭防火墙或创建高额计费资源。

---

## 3. 凭证与敏感数据零泄露

1. **绝对禁止硬编码**：
   - 严禁在代码、注释、提交历史、文档、输出日志中明文记录 API Key、Token、密码、证书私钥（`.pem`, `.key`, `id_rsa`）、生产环境连接串。
2. **误操作防御拦截**：
   - 包含密钥配置的文件（`.env.local`, `credentials.json` 等）必须在加入 `.gitignore` 之后方可使用；
   - 任何输出到终端或控制台的信息，涉及手机号、身份证、密钥等字段必须掩码脱敏。

---

## 4. 超大文件（>100KB）安全维护准则

针对老旧遗留代码或超大型源文件（如 >150KB 的核心管理器/协议解析器）：
- **定位精细度**：严禁盲目重构整块文件；改动前先通过精准行号或符号定义定位局部，仅做外科手术式微调；
- **风格一致性**：新增代码必须严格贴合当前文件原有的命名规范与缩进习惯，严禁在同一文件内混杂异构风格；
- **增量验证**：超大文件修改后，必须运行针对性单测或构建检查，确保无连锁破坏。
