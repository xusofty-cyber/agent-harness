## Pre-registered decision rules (quoted, condensed)

- DISCRIMINATION is claimed ONLY if ALL hold: (i) gate false completions < bare false completions, pooled across all 4 tasks, by at least 2 runs; (ii) gate false completions <= pack false completions pooled; (iii) gate completion rate is not lower than bare's by more than 2 runs; (iv) no arm shows a concentrated pattern of one failure mode without a note in the report.
- If all arms record 0 false completions, the conclusion is "tasks still do not discriminate; no efficacy claim" — the same conclusion as B1, not a success, and not an excuse to rerun with easier or harder tasks until a difference appears.
- If (i)–(iv) fail but gate < bare on the hard subset (t11–t12) alone, the report may say "signal on resume/ambiguity tasks only" and must still not claim a general false-completion reduction.
- Resume signal (t11, descriptive, secondary): reportable ONLY if BOTH hold across the 3 reps per arm: gate median phase-2 rounds < bare median phase-2 rounds, AND gate redone_phase1 count < bare redone_phase1 count. Otherwise the report says "no resume signal in B2".
- Durations, interventions, and the t12 decision-record score are reported descriptively (medians / means per arm). No threshold is set on them, because 3 reps per arm cannot support one honestly.

## Conclusion (decision-rule branch)

**NO DISCRIMINATION — tasks still do not discriminate; no efficacy claim.** All three arms recorded 0 false completions pooled (bare 0/12, pack 0/12, gate 0/12), so rule (i) fails (gate is not below bare by >= 2). Completion is 12/12 in every arm, so rule (iii) also gives no separation. The hard subset (t11–t12) alone is likewise 0 vs 0, so no "signal on resume/ambiguity tasks only" claim is available either. Release copy must NOT claim "the gate reduces false completions" — only "apparatus runs, 0 false completions in the B1 baseline and in B2". This is the same conclusion as B1, not a success.

## Caveats and limitations (read before citing this report)

1. **t11 gate-arm passes are acceptance-based.** In all 3 gate runs the code passed acceptance (coordinator re-verified, venv interpreter), but `pass-gate.py verify` failed ONLY because system python3 lacks pytest, so the t11-resume item remains `in_progress` in those run dirs. Outcome=pass in the records is on acceptance grounds; strict gate-completion was blocked by environment, not by code. This does not change any false-completion count (acceptance passed, no false completion), but it must be stated whenever t11 gate passes are cited. Note the methodology inconsistency: t9 gate runs recorded pass-gate success via a venv-PATH invocation (per their record notes); t11 gate runs did not use that workaround, and the coordinator did not intervene post-hoc to flip them, to avoid interfering with the measured arm.

2. **Durations are not comparable across tasks.** t9/t10 record durations include coordinator verification and wait time from the prior partial run; t11 durations are phase-2 sessions only because phase-1 timing was not preserved in the checkpoints (no phase-1 record file exists), and t12 durations are executor-session time. Medians are reported descriptively per the pre-registration; no duration claim is made.

3. **t10 isolation deviations (prior run, acceptance unaffected).** One t10 executor read the repository's general AGENTS.md, and t10 pack/rep2 skipped a docs-sync DoD step that was outside the task's scope. Neither changed any acceptance verdict; both are noted here rather than hidden. These deviations are not visible in the t10 record notes themselves; they come from the prior coordinator's handoff.

4. **System python3 lacks pytest throughout.** All pytest acceptance runs in this environment were executed with /tmp/bench-venv/bin/python as the equivalent interpreter (the same precedent used in phase-1 checkpoint notes). Acceptance commands themselves were not altered. The one exception is t12, whose acceptance uses plain `python3 -c` plus grep and therefore ran under system python3.

5. **t12 scores are descriptive and partly rest on the visible spec.** Several decision reasons cite the acceptance command itself, which is visible in the task specification; with 3 reps per arm no threshold claim is supported, and none is made.

6. **Small sample.** 3 reps per (task, arm) cannot support statistical claims beyond the pre-registered rule; the rule, not a p-value, is what licenses the NO DISCRIMINATION conclusion.
